# 秋招管理系统 PRD

> 本文件为产品需求的唯一权威版本。
> 最后更新：2026-08-12（第七版，岗位比较偏好同步与三轴评分）

## 一、背景与目标

秋招过程中信息分散、录入重复、AI 辅助缺失，导致管理成本高、流程易断裂。本系统以飞书 bitable 为数据中心，配套轻量网页前端，将岗位跟踪、简历管理、申请填表、面试准备整合为一套连贯流程。

**核心原则：**

1. 数据全在飞书，跨设备访问
2. 能用确定性脚本完成的不用 AI，保证稳定
3. 能自动维护的字段不让用户手动填
4. **写回 bitable 结构化字段必须经用户确认；追加写飞书文档不需确认**（只追加不覆盖，可追溯回滚）
5. 界面以操作效率和视觉清爽为优先

## 二、用户

需要跨设备管理秋招流程的单用户。系统应轻量、易维护，并允许非开发者通过浏览器完成主要操作；首版不考虑多人协作。

## 三、数据结构

飞书 Base 由部署者自行创建，并通过 `BITABLE_APP_TOKEN` 配置。

### 3.1 公司库

table_id 通过 `BITABLE_TABLE_COMPANY` 配置。

| 字段 | 实际类型 | 维护方式 | 说明 |
|------|----------|----------|------|
| 公司名 | text（主字段） | 新增/编辑公司 | 去除首尾空白后必填；规范化名称不可重复 |
| 官网链接 | text | 新增/编辑公司 | 存 URL 字符串 |
| 公司背景备注 | text | 编辑公司（选填） | 注入 Mock 面试上下文 |
| 备注 | text | 编辑公司（选填） | 公司级补充信息 |

公司是长期存在的一级对象，不因创建、修改或删除岗位而自动消失。用户可删除没有任何岗位关联的公司；已有岗位关联时必须先删除或迁移岗位，避免产生孤儿岗位。

### 3.2 岗位主表

table_id 通过 `BITABLE_TABLE_MAIN` 配置。

| 字段 | 实际类型 | 维护方式 | 说明 |
|------|----------|----------|------|
| 公司名 | text（主字段） | 创建岗位时自动快照 | 应用展示以公司库为准 |
| 公司ID | text | 创建岗位/迁移时自动写入 | 保存公司库 `record_id`，稳定关联键 |
| 岗位名 | text | 手动 | |
| JD | text | 手动粘贴 | |
| 官网链接 | text | 手动 | 存 URL 字符串，见下方说明 |
| 投递DDL | datetime | 手动 | |
| 内推码 | text | 手动 | |
| 状态 | select（单选） | 手动点选 | 待投/已投/笔试/一面/二面/三面/挂/offer |
| 星标 | select（单选） | 手动切换 | 选项仅 `星标`；用于标记下一批优先投递岗位，可随时清空 |
| 状态记录 | text | 状态变化时自动追加 | JSON 数组，记录 `at/from/to/resumeId`，用于查看进入已投、笔试、面试等节点的时间 |
| 简历编号 | text | 手动选择 or 生成后回填 | 格式严格为 `R{数字}`；待投可为空，已投及以后必填 |
| 准备文档链接 | text | 脚本自动创建回填 | 飞书文档地址 |
| 自我介绍-1min | text | AI 生成 + 用户确认保存 | |
| 自我介绍-3min | text | AI 生成 + 用户确认保存 | |
| 自我介绍-5min | text | AI 生成 + 用户确认保存 | |
| 自我介绍-英文版 | text | AI 生成 + 用户确认保存 | |
| 公司背景备注 | text | 手动（选填） | 注入 Mock 面试上下文 |
| 备注 | text | 手动 | |
| 附件 | attachment | **未使用** | 建表时的默认字段遗留，代码需忽略 |

一个公司可关联多个岗位。新建岗位必须选择公司并填写岗位名和 JD；状态默认为“待投”。进入已投、笔试、一面、二面、三面、挂或 offer 时，必须选择一份真实存在的简历。每次状态变化自动追加一条状态记录，用于追踪进入各投递阶段的时间。

岗位表保留公司名、官网、公司背景和备注作为飞书内可读快照及旧数据兼容字段。公司改名或修改官网后，应用通过公司ID读取最新公司信息；首版不批量重写既有岗位快照。

对使用者的影响：`官网链接` / `准备文档链接` 在飞书界面里点不开（飞书不支持 url 字段类型，实际存的是纯文本），要能点击得在飞书里手动把字段类型改成「超链接」。字段类型层面的实现约束见 `CLAUDE.md`。

### 3.3 经历库

table_id 通过 `BITABLE_TABLE_EXPERIENCE` 配置。

| 字段 | 实际类型 | 维护方式 | 说明 |
|------|----------|----------|------|
| 经历标题 | text（主字段） | 手动 | 一段完整实习、项目或比赛经历是最小单位，不继续按模块拆分 |
| 经历类型 | select（单选） | 手动 | 实习经历/项目经历/校园经历/荣誉/获奖/语言/证书/其他；申请表助手只按该字段归类，空值或其他进入待确认 |
| 经历摘要 | text | 手动或 AI 草稿确认后保存 | 快速说明职责、行动和量化结果，供展示、JD 匹配和简历生成 |
| 技能标签 | multiselect（多选） | 手动 | 记录经历体现出的能力，不记录 Figma、SQL、Python 等工具名 |
| 经历正文 | text | 手动（Markdown） | 权威内容，建议包含 Overview、What I Did、Key Challenges、Reflection、Possible Interview Questions |
| 相关链接 | text | 手动 | 保留作品、文档、数据看板、复盘材料等外部链接，不并入正文后删除 |
| 追问记录 | text | 手动或 Mock 面试后确认追加 | 保留面试暴露出的追问、回答方向和复盘，不并入正文后删除 |

**标签约束：** 多选字段写入不存在的选项会直接报错，不会自动创建选项。应用必须读取飞书「技能标签」字段的真实选项并按同一集合校验，不能在代码里维护另一份“推荐标签”。用户后续在飞书新增选项后，应用刷新即可使用；新增标签仍属于字段结构变更，需用户确认后执行。

旧「STAR全文」「50字版」「100字版」迁移到「经历正文」「经历摘要」后暂时保留，但应用不再展示或写入；删除旧字段需在核对迁移结果后另行确认。「相关链接」「追问记录」是继续保留的正式字段，不能作为废弃字段删除。

### 3.4 简历库

table_id 通过 `BITABLE_TABLE_RESUME` 配置。

| 字段 | 实际类型 | 维护方式 | 说明 |
|------|----------|----------|------|
| 编号 | text（主字段） | 脚本自动分配 | `R1`/`R2`/…，严格 `^R(\d+)$` |
| 版本名 | text | 手动 | 如「产品方向-字节版」 |
| 适用方向 | text | 手动 | |
| 正文内容 | text | 手动更新 | AI 读取用副本，权威版本在用户 Word 文件 |
| 投递记录 | text | 脚本全量重算 | 如「字节-产品策略经理、腾讯-ACG产品经理」 |
| 创建时间 | datetime | 脚本自动填入 | |

### 3.5 偏好设置

table_id 通过 `BITABLE_TABLE_PREFERENCE` 配置。可用 `npm run migrate-preferences -- --yes --write-env` 创建并写入本地 `.env`。

| 字段 | 实际类型 | 维护方式 | 说明 |
|------|----------|----------|------|
| 配置名 | text（主字段） | 脚本自动创建 | 当前固定为「默认偏好」 |
| 阶段策略 | select（单选） | 岗位比较页编辑 | 练手/均衡/冲刺/兜底 |
| 求职价值权重 | number | 阶段策略自动带出 | 练手 30、均衡 40、冲刺 70、兜底 20 |
| 练手价值权重 | number | 阶段策略自动带出 | 练手 55、均衡 40、冲刺 20、兜底 25 |
| 兜底价值权重 | number | 阶段策略自动带出 | 练手 15、均衡 20、冲刺 10、兜底 55 |
| 价值取向 | text | 岗位比较页编辑 | 长期方向、想去/不想去的业务或公司特征、文化偏好等 |
| 更新时间 | datetime | 保存时自动写入 | 用于追踪同步状态 |

偏好设置是跨设备同步配置，不属于单次比较结果。阶段策略解释：练手 = 优先面试训练价值；均衡 = 同时看岗位价值和练手机会；冲刺 = 优先真正想去、长期方向匹配且值得认真准备的岗位；兜底 = 优先门槛友好、准备成本低、更可能推进的岗位，不等于随便投。

**编号分配规则：** 读取全部编号，用 `^R(\d+)$` 正则提取数字，取最大值 +1。不匹配该格式的编号（如用户手填的 `R1-字节版`）在计算时忽略，不复用已删除编号的空缺。

### 3.6 复盘表

table_id 通过 `BITABLE_TABLE_REVIEW` 配置。可用 `npm run migrate-reviews -- --yes --write-env` 创建并写入本地 `.env`。

| 字段 | 实际类型 | 维护方式 | 说明 |
|------|----------|----------|------|
| 复盘标题 | text（主字段） | 保存时自动生成 | `字节跳动-产品运营 一面 2026-09-02` |
| 岗位记录ID | text | 保存时写入 | 关联岗位主表 `record_id` |
| 公司名 | text | 保存时写入 | 快照，仅为飞书内可读 |
| 岗位名 | text | 保存时写入 | 快照 |
| 面试轮次 | text | 用户选择 | 笔试/一面/二面/三面/HR面/其他 |
| 面试时间 | datetime | 用户选择 | |
| 内容来源 | text | 自动判定 | 本地转写/粘贴文本/Mock 面试 |
| 复盘文档链接 | text | 建文档后回填 | 正文唯一权威位置 |
| 录音文件名 | text | 转写后写入 | 只存文件名，不存录音本体 |
| 录音时长秒 | number | 转写后写入 | |
| 转写字数 | number | 保存时计算 | |
| 一句话结论 | text | 用户填或从点评摘出 | 供横向浏览 |
| 点评状态 | text | 自动判定 | 未点评/已点评 |
| 更新时间 | datetime | 每次追加写文档后更新 | |

**枚举字段一律用 text 不用 select。** 飞书 select 写入不存在的选项会直接报错（和「技能标签」同一个坑），取值合法性由后端常量数组（`INTERVIEW_ROUNDS`、`REVIEW_SOURCES`、`REVIEW_COMMENT_STATUSES`）校验。

**正文不进表字段。** 逐字记录、我的补充、AI 点评三块正文只存在复盘文档里，表里绝不存副本，避免两处权威打架。

## 四、功能模块

| 编号 | 模块 | 做什么 | AI / 脚本 | 写回是否需确认 |
|------|------|--------|-----------|----------------|
| F0 | 公司库与岗位看板 | 公司库增删改；公司下创建岗位；岗位按状态分列，星标岗位同状态优先展示，待投按 DDL/加入时间催办 | 无 | 删除公司需确认 |
| F1 | 岗位详情 | 编辑岗位名、JD、状态、简历、DDL 等岗位字段 | 无 | 用户自己在编辑 |
| F2 | 准备文档 | 新建飞书文档并回填链接，面试复盘由用户在文档里写 | 脚本 | 追加写文档不需确认 |
| F3 | 简历库 | 列版本；可指定已有版本，或按 JD 从经历库选择素材生成新版本后存为新编号 | AI 出草稿 | 需确认后保存 |
| F4 | 经历库 | 七字段新建、编辑与批量导入；可根据正文生成摘要草稿；沉淀相关链接和面试追问 | AI 出草稿 | 需确认后保存或追加 |
| F5 | 申请表助手 | 固定展示实习/项目/校园/荣誉/语言证书资料架，按经历类型归类并由近到远排序、展开逐字段复制；不确定分类单独列出待用户确认；开放题可额外粘贴 → 拆题 → 结合 JD、简历和经历库生成 → 多轮改稿 | 确定性整理 + AI开放题 | 不写回，直接复制粘贴 |
| F6 | 面试准备材料 | 按 JD + 简历生成高频题和准备重点 | AI | 可追加写准备文档 |
| F7 | 自我介绍 | 挂在岗位上，1/3/5min + 英文四版 | AI 出草稿 | 需确认后写回主表 |
| F8 | Mock 面试 | 按 JD、指定简历和公司背景多轮对话；结束后出摘要 + 追问建议；对话可导出 md | AI | 面试问题追加到追问记录前需用户逐条确认 |
| F9 | 岗位比较 | 独立页面按公司批量选岗；读取同步偏好和本次补充标准，按求职价值/练手价值/兜底价值三轴横向比较岗位 | AI，结构化结果 | 偏好需保存写回；结果保存在浏览器 |
| F10 | 面试复盘 | Mock 面试页内「真实面试复盘」tab：导入音频/MP4 本地转写（或粘贴转写文本）→ 校对整篇带时间戳和角色前缀的转写文档 → 我的补充 → 结构化点评 → 新建飞书文档写正文 + 复盘表记元数据和文档链接 | 本地 ASR + 规则预标角色 + AI 点评 | 保存到飞书需确认；后续追加写文档不需确认 |

**岗位比较规则（F9）：** 支持单岗位勾选和公司全选/清空；公司全选不受数量限制，但单次 AI 分析限 2–20 个岗位。页面读取「偏好设置」中的阶段策略和价值取向，另允许输入不超过 500 字的本次补充标准。每个岗位必须拆成三轴：求职价值（岗位本身是否值得认真投入，综合长期方向、个人意愿、公司/业务吸引力、简历匹配）、练手价值（能否训练后续真正需要的面试能力、失败机会成本是否低）、兜底价值（JD 门槛是否友好、准备成本是否低、是否更可能推进到笔试/面试）。综合分按当前阶段权重计算，再叠加专业与技术背景调整并四舍五入；同分保持用户选择顺序。结果必须展示冲突提示，例如“简历契合高但高压文化与偏好冲突”。逐岗分析必须按 JD 要求逐条拆解，标注符合、部分符合、缺口或信息不足。页面中阶段和评分维度均提供 hover 解释。综合分只用于横向浏览，不生成建议投递顺序。

**投递记录的维护方式（F3 关键）：** 主表「状态」或「简历编号」任一变化，就全量重算简历库的「投递记录」。不做增量——改简历编号、状态回退、删岗位都会让增量结果错。只统计已投出去的岗位（状态不是「待投」）。

**本地保存与同步（F3 关键）：** 岗位详情页的字段修改先写入前端状态和 `localStorage` 的待同步队列，再后台上传。网络失败、刷新或重开页面后，队列会继续重试；待同步岗位和全局顶部条都要显示状态，避免用户误以为已经完全落库。

**Mock 面试的上下文（F8 关键）：** 只注入 JD + 指定简历 + 公司背景备注，不注入完整经历库。经历库全文会稀释模型注意力，且无状态设计下每轮都要重传，token 随轮次线性叠加。F8 和 F10 是两条独立链路：F8 复盘的是 AI 生成的模拟对话，结果可逐条确认后写进经历库「追问记录」；F10 复盘的是真实面试录音，只产出结构化点评，不写回经历库。

**面试复盘的边界（F10 关键）：** 转写只在本地可用——线上无状态、请求体上限 4.5MB、跑不了 Python，`/api/health` 的 `transcribeEnabled` 为 false 时前端禁用本地上传入口，降级为粘贴/上传转写文本。转写引擎（sherpa-onnx + SenseVoice int8，纯 CPU）没有说话人分离，用「VAD 时间戳分段 + 确定性规则预标角色 + 用户直接编辑整篇文档角色前缀」补齐，不引入声纹模型，也不花 AI token 去猜角色。音频/MP4 只在服务端临时落盘，转写完立即删除，不入库不入日志。

**申请表助手的核心理解（F5 关键）：** 多数网申页面的实习、项目、校园、荣誉、语言证书是可重复字段组，不是开放题。页面默认从经历库整理这些固定资料架，归类只读取「经历类型」，不再根据标题或正文硬猜；空值、其他或未知类型必须单独列出让用户确认。实习/项目/校园读取「经历摘要」并以 bullet 排版展示；荣誉/获奖、语言/证书读取「经历正文」中的原文行，每行拆成独立条目（时间 + 奖项名/证书名 + 说明）。网页复制来的开放题才进入拆题和生成链路。开放题生成时注入 JD、指定简历和经历知识库，由模型按题目选择最相关的具体经历；不把内容写回任何表。

## 五、技术架构

```
浏览器（public/，Vue 3 CDN，无构建步骤）
   │  fetch /api/*，请求头带 X-Auth-Token
   ▼
src/api/index.js（路由表）── src/http/app.js（匹配 + 口令校验 + 错误包装）
   │                              ▲
   │                    两个入口共用同一个 handle：
   │                    本地 src/dev-server.js ／ 线上 api/[...path].js
   ├── src/storage/   飞书 bitable REST 读写
   ├── src/llm/       DeepSeek 调用 + prompts/ 模板加载
   └── src/services/  确定性逻辑（投递记录重算、编号分配、飞书文档、复盘分段与点评拼装）
```

本地另有 `tools/transcribe/`：独立 venv 的 Python 转写脚本 + 模型，不属于 Node 依赖，Node 侧只通过 `child_process.spawn` 按行读它的 JSON 输出。

**关键决策：**

1. **数据层走飞书 REST OpenAPI，不用 lark-cli。** lark-cli 是本地二进制，Vercel 上不存在，`execFile` 必然失败。改用自建应用的 `tenant_access_token`。前提是该应用已被加为 bitable 协作者（`full_access`），否则读得到、写报 91403。
2. **零依赖。** 环境变量用 Node 原生 `--env-file`，HTTP 用原生 `fetch`，前端用 Vue CDN。不需要 `npm install`，换电脑直接跑。本地语音转写是仓库外部工具（独立 venv + 系统 ffmpeg），不破坏这一条。
3. **中英字段名映射层（`src/storage/schema.js`）。** 飞书里字段名是中文，代码里用英文 key，所有读写都经过这一层翻译，并按字段真实类型做序列化。表里多出来的字段（如未使用的「附件」）在这一层被忽略，不会被误写。
4. **记录用 `record_id` 定位，不用业务字段。** 三张表都没有唯一业务 ID，公司名和岗位名都可能重复。
5. **无状态会话。** Mock 面试和申请表助手的 `history` 由前端持有，每次请求带完整上下文。Vercel Functions 跨请求不保内存。
6. **口令保护。** 公网 URL 后面是简历、JD、面试复盘和 API 额度。公网未配置 `APP_PASSWORD` 时受保护接口拒绝访问；登录成功后只向浏览器签发 12 小时有效的签名会话，不传回或持久化原始口令。
7. **prompt 存 md 文件。** 运行时读取，改 prompt 不改代码。模板只支持 `{{变量}}` 替换，条件分支由调用方拼好再传入。

## 六、不做的事

- 不自动抓取招聘信息（信息渠道太杂，人工搜索保留）
- 不做简历 PDF/HTML 排版导出（用户已有 Word → AI 排版的工作流）
- 不做消息推送（飞书 bitable 自带 DDL 提醒）
- 不做微信桥接
- 不做简历版本 diff，只存快照
- 不做多用户、不做登录体系，单用户 + 一个口令
- 不在岗位主表或复盘表里存面试复盘正文，正文写在飞书文档里（准备文档，或每场真实面试各自的复盘文档），表内只存元数据与链接
- 不做说话人声纹分离，角色靠规则预标 + 用户纠正
- 不在服务端保存录音文件，转写完即删
- 不把 AI 点评或追问写回经历库（F10 只产出结构化点评）
- 不做云端 GPU 转写部署
